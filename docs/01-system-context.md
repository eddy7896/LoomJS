# 01 — System Context

## The product in one paragraph

loomJS is a **web-based visual programming language (VPL) with Figma-style design tools**.
Designers build full-stack, data-driven web apps by *designing UI on artboards* and *wiring
visual nodes* — never by writing syntax. The node graph is an **intermediate representation
(IR)**; a Node.js compiler emits a real, runnable, *owned* codebase: **Vite + React +
TypeScript** frontend, **Vercel serverless** backend, wired to the user's **own Supabase**
database and auth. The core promise is: *a designer should never feel they left the canvas.*

## The designer's language (metaphor mapping)

Programming concepts are re-expressed as design concepts. Preserve these metaphors:

| Programming concept | loomJS surface |
| --- | --- |
| Component / screen | UI designed on an **artboard** |
| Function / logic | **FN** node with typed in/out ports |
| API endpoint | **API route** node |
| State / variable | **STATE** node |
| Database table | **DB** node (generated by the connector from real schema) |
| Calling / passing data | a **wire** from an output port to an input port |
| Navigation / user flow | a **flow arrow** between artboards (compiles to a route + guard) |
| Compilation | **Compile / Generate** → real React + serverless repo |

## The two modes (one canvas)

1. **Design mode** — Figma-style UI + user-flow editor, **frontend only**. Left panel is the
   UI component **palette** (Frame, Text, Input, Button, etc., plus imported kit components).
   The canvas holds **artboards** (screens) built from real rendered components, with **flow
   arrows** between them. Right panel is the **inspector** (schema-driven properties + backend
   binding).
2. **Nodes mode** — the **backend graph**. Left panel is the node palette (UI/FN/API/STATE/DB).
   Nodes are wired port-to-port into pipelines. Right panel inspects the selected node's ports
   and its **compiled output** (node ↔ code lineage).

## BYO-backend — the defining architectural stance

**Bring Your Own Backend.** loomJS owns the *building experience*; the user owns the *running
app's infrastructure*.

- The user connects **their own Supabase** (database + auth) via the connector, and deploys to
  **their own Vercel**. loom never hosts, stores, or becomes liable for end-user app data.
- loom *brokers* the user's credentials (held in the encrypted env bucket) to reach their
  Supabase during Preview and to inject into Vercel at Deploy.
- This is the honest extension of "you own real code": the user owns the code **and** the
  database **and** the deployment. Strongest possible answer to "am I locked in?" — no.
- It also matches the **open-source future**: an OSS loomJS can't host backends for everyone;
  BYO-backend scales to a community where anyone runs loom and connects their own stack.

Trade-off accepted: the hard problem moves from *hosting* to *connection onboarding UX*. The
connect-your-Supabase step is where non-technical users stall, so it gets real design care
(manual-with-instant-validation now; OAuth one-click later).

## How we got here (reframe history — so decisions aren't relitigated)

The project evolved through deliberate reframes. Each is settled:

1. **From "app builder" → "visual programming language."** loomJS is a *language*, which
   raises the generality bar — countered by the **scope-ceiling discipline**: it's a
   *domain-specific* VPL for data-driven web apps, with the **Code node** as escape hatch.
2. **Multi-framework → React-family only (web), then web-only for V1.** IR-with-adapters lets
   frameworks be emit targets. React Native and non-React frameworks (Vue/Svelte) are
   explicitly out — a second component model is a different product.
3. **Multiplayer live-editing → deferred → Git-style async branch/merge.** Live CRDT
   multiplayer was dropped from V1 (worthless before the compiler works; forces a distributed
   foundation before the model stabilizes). Replaced with an async fork/branch/merge model
   (v2) that needs versioning + semantic graph-merge, not realtime sync. The document stays
   **branch-ready now** (stable ids, atomic ops) so re-adding is cheap.
4. **Managed backend → BYO-backend.** (Above.)

## Example app (illustrative only)

**Fintrack**, a personal finance tracker (auth, dashboard, transactions, budgets, accounts),
is used throughout as a *sample* that stresses the real requirements (relations, forms, CRUD,
derived data, empty/loading/error states, auth context). **It is not the product spec** — do
not bake finance-specific assumptions into the system.

## Who it's for

UI/UX designers who want to ship real full-stack apps without writing syntax, and who want to
own the resulting code and infrastructure. The "never left the canvas" promise means every
programming concept must have a calm, literal, designerly surface — and anything that can't
get one goes to the Code node rather than forcing syntax onto the designer.
